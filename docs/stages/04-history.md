# 阶段 4：多任务、历史与刷新恢复

状态：实现、自动化验证及双轴代码审查完成。前置条件：阶段 3 的任务可创建、执行并查询。契约见 [规格第 3、4.5、6 节](../SPEC.md)。

## 目标与交付

用户可连续创建任务，随时查看自己的历史；每个未完成任务独立更新，刷新后从 Java 恢复。历史页面、任务卡片、查询层和必要测试均需交付。页面视觉调整使用 `frontend-design`；代码使用 `karpathy-guidelines`。

## 后端

1. 实现 `GET /api/tasks`：根据服务端当前演示用户过滤，按 `created_at DESC` 和 ID 的确定性顺序返回任务；字段包括任务 ID、模板 ID/标题、状态、阶段、创建时间、结果或失败原因。原题不要求分页，当前可先返回完整演示数据；若增加分页，前端必须能发现和跟踪所有已加载的未完成任务，并说明范围。
2. 复用单任务读取逻辑与统一错误格式，不允许由用户传入其他用户 ID 绕过过滤。记录查询错误，不在读取时更新状态。
3. 验证历史记录在容器重启、数据库和文件卷保留后仍可访问；未完成任务跨进程恢复不在范围。

## 前端状态设计

1. 用当前用户构造查询键，例如 `['tasks', userId]` 和 `['task', userId, taskId]`；每个任务独立保存服务端状态及查询错误，上传/提交状态不与任务状态混用。
2. 历史页先查询后端；对返回的 `PENDING`、`RUNNING` 任务启用独立轮询，例如每 2–3 秒。服务端给出 `SUCCEEDED` 或 `FAILED` 后立即停掉该任务轮询；没有未完成任务时无轮询。可以暂停或继续当前页面以外的跟踪，但重新进入页面必须重新读取恢复。
3. 提交成功后立即展示该任务，结束“提交中”并允许再次提交；通过更新或重新获取历史列表纳入任务。不同任务的数据按 ID 合并，不能使用单个全局 `status` 覆盖全部卡片。
4. 单次查询失败时保留最近一次成功数据，显示“状态暂时无法更新”和重试入口；请求失败不得构造 `FAILED`。服务端返回 `FAILED` 时展示真实阶段与原因。用户点击恢复查询时重新请求，仍按终态停止规则处理。
5. 刷新后从后端历史恢复并识别未完成任务；无需依赖仅保存在内存中的任务列表。切换用户时取消旧查询、清空或隔离旧用户相关数据、重置上传位并查询新用户；网络响应迟到时通过查询键和取消/代次控制防止覆盖。
6. 离开相关页面取消计时器、订阅与可取消请求；确保页面重新进入时正常恢复。图片预览、创建时间、处理中阶段、成功结果、失败原因、加载、空历史和请求失败都有明确展示，键盘和小屏可操作。

## 验证

- A06：两个任务以交错顺序返回，断言 ID、状态、错误与结果分别正确。
- A07：先获得 `RUNNING`，再模拟查询失败；页面保留原状态并显示请求错误，恢复后可显示服务端最终状态。
- A08：使用假计时器验证终态不再请求；全部任务完成后没有自动请求；切换用户或卸载后迟到响应不更新当前页面。
- 后端验证用户 A、B 历史和单任务均隔离，排序稳定；空历史与异常响应正确。
- 容器手工验证：并发创建两项、刷新、离开再返回、模拟查询暂时失败和恢复、切换用户；记录网络请求以确认终态停止跟踪。
