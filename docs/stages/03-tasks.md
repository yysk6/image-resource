# 阶段 3：任务受理与异步执行

状态：待实施。前置条件：阶段 2 可上传并读取受控素材。契约见 [规格第 4.3、4.4、5、6 节](../SPEC.md)；本阶段重点是后端真实步骤与数据库状态。

## 目标和边界

请求完成校验并创建任务后立即受理，后端在独立线程顺序执行素材检查、模拟生成、结果整理；任务在用户关闭页面后继续执行。单实例进程崩溃或重启后不承诺恢复；结果以 MySQL 为准，不能由查询推进。代码实现使用 `karpathy-guidelines`；如实施集成测试，按项目规则使用 `tdd` 技能。

## 数据与接口

1. 迁移创建 `creation_task` 和 `task_asset`，包括规格所列字段、用户/创建时间索引、顺序约束和必要外键；有序关联用于恢复上传位置。
2. 实现 `POST /api/tasks`，接收 `templateId` 和有序 `assetIds`。校验用户、模板、数量、素材归属、类型、大小及文件存在性；对重复素材是否允许作出明确实现，推荐同一任务不接受重复素材 ID 并给出可读提示。
3. 实现 `GET /api/tasks/{id}`，按任务 ID 和当前用户查询；其他用户及不存在均返回 404。返回字符串 ID、模板信息、状态、阶段、结果、错误及 ISO 8601 时间，查询保持只读。

## 受理与调度顺序

1. 应用服务在短事务内校验并插入 `PENDING` 任务及素材关联；数据库提交后再把任务 ID 提交至执行器。避免 Spring 同类内部调用使事务/异步代理失效，结构上将事务服务和调度服务分开或采用等效可靠方式。
2. 使用有限线程数与有限队列的 `ThreadPoolTaskExecutor`；配置线程名前缀、最大队列、拒绝策略，关闭时等待策略有明确配置。耗时步骤不可在 HTTP 线程执行，禁止使用 `CallerRunsPolicy` 导致请求等待完整任务。
3. 若提交执行器被拒绝，使用新事务将仍为 `PENDING` 的任务更新为 `FAILED`，写入系统繁忙原因并返回 503；只有成功交给执行器后返回 202。若失败状态写入也失败，记录任务 ID 和错误，返回服务端错误，明确运维限制；不能报告已成功受理。
4. 数据库提交后、入队前如果进程崩溃，任务可能停留在 `PENDING`；工作中途崩溃可能停留在 `RUNNING`。本阶段不实现自动恢复，在 README 明确人工排查及处理方式，避免承诺队列可靠投递。

## 执行步骤与状态机

```text
PENDING → RUNNING/MATERIAL_CHECK → RUNNING/GENERATING
        → RUNNING/FINALIZING → SUCCEEDED
PENDING → FAILED（入队拒绝）
RUNNING/任一步骤 → FAILED（记录当前失败阶段）
```

1. 执行器取得任务后，通过条件更新将 `PENDING` 置为 `RUNNING` 并设置 `started_at`；任务已处于终态时退出。进入每步前，以短事务保存阶段；不在数据库事务中 sleep 或执行耗时操作。
2. 分离三个可单独观察的步骤：检查素材仍存在且可读取；按配置延迟并模拟生成；整理结果、生成或引用项目内可访问的示例图片。阶段变化必须来源于 Java 和数据库。
3. 每步从配置读取延迟；配置一个 `none/material-check/generate/finalize` 失败点，固定触发以复现。测试使用可注入时钟/等待器或其他方式避免真实长时间等待，不依赖随机失败。
4. 步骤抛错时立即停止后续步骤，以条件更新持久化 `FAILED`、失败阶段、可理解原因和 `finished_at`；日志包含任务 ID 和阶段。系统内部错误记录细节但不将堆栈暴露给用户。
5. 全部成功后保存可访问的 `result_url`、`SUCCEEDED` 和 `finished_at`。数据库更新设置允许的前置状态，确保成功或失败后不能被迟到更新覆盖；结果资源在容器重启后仍能访问。
6. 前端详情页在素材就绪后发送创建请求；提交中禁用按钮，受理后展示新任务并结束“提交中”，允许再次创建。阶段 4 实现完整的独立跟踪与历史。

## 验证

- A01：用受控步骤记录调用顺序，验证检查、生成、整理各执行一次。
- A02：分别注入三个阶段失败，断言后续步骤未运行、失败阶段和原因持久化。
- A03：成功后结果 URL 可读取；终态条件更新失败，查询不更改状态。
- A04：缺少素材、错误数量、重复 ID、类型/大小不符、文件不存在、跨用户素材及任务查询均被拒绝。
- A05：用可控的拒绝执行器验证 503 和失败记录；验证状态写入异常不被报告为成功。
- 容器验证：设置足够长的延迟，测量请求在步骤结束前返回 202，关闭浏览器后重新查询完成；连续提交多个任务，验证排队/并发；检查数据库中阶段及结果。
